Create a workload identity

Five rules shape this flow:

  • Step by step, like the Claude Console "Connect workload" wizard.
  • The most needed fields are shown directly, required ones first.
  • No breaking changes. The API, the stored fields and generated workflows stay as they are. Every token that signs in today still signs in.
  • One path for every identity. Create and edit read and write the same stored fields; no special handling for identities made by the old form.
  • Rare values are prefilled, not hidden. Like Claude's Issuer step, the issuer and the audiences are visible, prefilled fields. A field is not hidden just because it is optional. No step needs an Advanced section now.
Example: repository boojack/bb-gitops, Bytebase project gitops-elg0, GitHub Actions

The dialog has a fixed height: 680px, or the window height minus 64px when the window is smaller. Back, Cancel and Continue stay in the same place on every step. A short step leaves space above the buttons, and a long one (step 4, or step 2 while editing) scrolls inside the step body. Fields keep room for their focus ring, so no border is cut at the edge of the scroll area.

The rename warning shows only for GitHub, while Owner ID is empty. It names the risk (the account is renamed or deleted and someone registers the name), what that person could do (sign in as this identity), and the fix (add the owner ID). It ends with a link to GitHub's changelog post on immutable subject claims, the one external link in the dialog. GitLab has no ID field and shows no warning. Subject pattern is the one stored rule (no new fields). The form builds it: Owner only gives repo:boojack/*, with Repository repo:boojack/bb-gitops:*, with Owner ID repo:boojack@123/bb-gitops:*. The server accepts both GitHub subject formats for this pattern since bytebase#21931 (BYT-10349, merged). The GitOps page reads Owner and Repository from the same pattern, so its parser drops the @ID parts; otherwise its repository link would read github.com/boojack@123/bb-gitops.

Workload identity created

Jobs in boojack/bb-gitops can now sign in to project gitops-elg0 as this identity.

Email
bb-gitops-ci@gitops-elg0.workload.bytebase.com Copy
Set it as BYTEBASE_WORKLOAD_IDENTITY in your workflow. Workflows generated on the GitOps page already use it.

Check that it signs in (optional)

Run this workflow once to confirm the identity works before you rely on it.

.github/workflows/bytebase-wif-test.yml
Copy
name: bytebase-wif-test
on:
  push:
    paths:
      - .github/workflows/bytebase-wif-test.yml
permissions:
  id-token: write
  contents: read
jobs:
  sign-in:
    runs-on: ubuntu-latest
    steps:
      - name: Fetch GitHub OIDC token
        run: |
          OIDC_TOKEN=$(curl -sS --fail -H "Authorization: bearer $ACTIONS_ID_TOKEN_REQUEST_TOKEN" \
            "$ACTIONS_ID_TOKEN_REQUEST_URL&audience=bytebase" | jq -r .value)
          echo "::add-mask::$OIDC_TOKEN"
          echo "OIDC_TOKEN=$OIDC_TOKEN" >> $GITHUB_ENV
      - name: Exchange for a Bytebase access token
        run: |
          RESPONSE=$(curl -sS --fail-with-body https://cloud.bytebase.com/v1/auth:exchangeToken \
            -H "Content-Type: application/json" \
            -d '{"token":"'"$OIDC_TOKEN"'","email":"bb-gitops-ci@gitops-elg0.workload.bytebase.com"}') \
            || { echo "Sign-in refused: $RESPONSE"; exit 1; }
          echo "$RESPONSE" | jq '.accessToken = "<redacted>"'
Commit this file on any branch of boojack/bb-gitops and push. It runs when this file changes, not on every push. A green job means the identity signs in; a red job prints the reason Bytebase refused the token.
Done

Everything is created when you leave step 3. Step 4 is the done screen: the one value the workflow needs, plus an optional test. Compared with Claude's Test step, the test is optional and sits in its own section, runs only when its own file is pushed, on any branch, so it needs no PR to a protected main, the dialog does not listen for the result (the job log shows it), and there is no setup-guide link. The URL in the snippet is the workspace's External URL; when it is not set, the section asks for it instead of showing a snippet. When the flow starts from the GitOps page, the text says the generated workflow already signs in, so running it is the test.

Editing reuses steps 1 to 3 with a banner, as Claude does. The provider is locked when editing, like the email, so a stored pattern is never rebuilt in another format. When no provider is stored, the provider cards start empty and required, as on create, because the server refuses a save without one. Every save sends back the stored JWKS URL unchanged, also for GitHub and GitLab where the field is not shown. The steps load what is stored: the issuer, the audiences, and the subject pattern, with Owner, Owner ID and Repository read from it. There is no separate path for identities made by the old form.
